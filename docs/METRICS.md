## 1. Общие правила

### 1.1. Единица подсчёта

**Тест** — уникальный тестовый метод из `test-inventory.json`, идентифицируемый полем `id`.

- Параметризованный тест (`@ParameterizedTest`) считается **одним тестом** на уровне инвентаризации, а не количеством наборов параметров.
- `@RepeatedTest` также считается **одним тестом**.
- Абстрактные/базовые классы без тестовых методов не добавляют тесты в инвентаризацию.
- Классификация по типу: **API** или **UI**.
- Критичность берётся из Allure `@Severity`; для дашборда особо выделяется `CRITICAL`.
- `@Disabled` означает отключение теста в коде. Причина `BUG:` используется отдельно для учёта времени восстановления.

**Важно:** подсчёт уникальных тестов отличается от числа JUnit-инвокаций. Например, один параметризованный метод с пятью наборами данных остаётся одним тестом в инвентаризации.

### 1.2. Статусы выполнения

| Статус | Смысл |
|---|---|
| `PASSED` | Тест успешно выполнен |
| `FAILED` | Ошибка проверки / assertion |
| `BROKEN` | Ошибка выполнения теста |
| `SKIPPED` | Тест пропущен во время выполнения |
| `NOT_RUN` | Активный тест не имеет результата выполнения |
| `DISABLED` | Тест отключён в исходном коде |

`FAILED` и `BROKEN` — разные статусы выполнения; слово `BROKEN` здесь **не** является маркером времени починки. Для последнего используется только префикс **`BUG:`** в `@Disabled`.

### 1.3. Временные окна

- **Last Test Results** — последний оцениваемый CI-запуск.
- **Historical Test Results** — до **10 последних CI-запусков** соответствующей ветки; не все записи обязаны содержать нужные поля.
- **Team Efficiency** — последние **30 календарных дней** для завершённых циклов починки и первых одобрений PR; две метрики очереди PR отражают текущий момент.
- Длительности починки и PR review — **календарное время**, включая ночи, выходные и праздники.

### 1.4. Значение `N/A`

`N/A` означает, что метрику нельзя корректно вычислить: нет истории, нет подходящих наблюдений, не было завершённых событий либо отсутствует исходный файл. **`N/A` не равно нулю.**

## 2. Release Readiness Status

**Что показывает:** агрегированную оценку готовности релиза на основании результатов критических тестов, покрытия критических функций и результата CI.

| Статус | Значение |
|---|---|
| `READY` | Все применимые критерии готовности выполнены |
| `NOT_READY` | Обнаружено блокирующее условие |
| `UNKNOWN` | Недостаточно данных для уверенного решения |

**Формула:** это **не процент**, а результат набора логических проверок, выполняемых `ReleaseReadinessCollector`. В Dashboard выводятся итоговый `status`, массив `reasons` (блокирующие причины) и `warnings`.

**Известные блокирующие причины из текущего отчёта:** упавшие/сломанные критические тесты, отключённые критические тесты, неуспешный CI. Также в оценке используется покрытие критических функций. Точные условия и пороги необходимо смотреть в актуальной версии `ReleaseReadinessCollector.java`; не следует подменять их произвольной формулой вроде «Pass Rate > 90%».

**Пример:** при 7 неуспешных критических тестах, 3 отключённых критических тестах и неуспешном CI статус — `NOT_READY`, даже если Critical Feature Coverage равен 100%.

**Источник:** `target/metrics/release-readiness.json`.

## 3. Test Overview

Общая инвентаризация тестов в исходном коде, независимо от результатов последнего запуска.

| Метрика | Что означает | Формула / правило |
|---|---|---|
| **Total Tests** | Общее число уникальных тестов | `COUNT(inventory.tests)` |
| **Active Tests** | Тесты без эффективного `@Disabled` | `COUNT(disabled = false)` |
| **Disabled Tests** | Тесты с эффективным `@Disabled` | `COUNT(disabled = true)` |
| **API / UI** | Разделение тестов по типу | `COUNT(type = API) / COUNT(type = UI)` |

**Контрольные соотношения:**

```text
Total Tests = Active Tests + Disabled Tests
Total Tests = API Tests + UI Tests + Unclassified Tests
```

Последнее равенство предполагает учёт неклассифицированных тестов, если они появились; Dashboard показывает только API и UI.

**Пример:** 98 тестов = 80 активных + 18 отключённых; 74 API + 24 UI.

**Источник:** `target/metrics/test-inventory.json`, поля `summary` и `tests`.

## 4. Last Test Results

Статусы уникальных тестов для текущего оцениваемого CI-запуска.

| Метрика | Что означает | Формула / правило |
|---|---|---|
| **Pass Rate** | Доля успешных среди выполненных | `Passed / (Passed + Failed + Broken) × 100%` |
| **Tests Passed** | Успешные тесты | `COUNT(status = PASSED)` |
| **Tests Failed** | Ошибки проверок | `COUNT(status = FAILED)` |
| **Tests Broken** | Ошибки выполнения | `COUNT(status = BROKEN)` |
| **Tests Skipped** | Пропущенные при выполнении | `COUNT(status = SKIPPED)` |
| **Tests Not Run** | Активные тесты без результата | `COUNT(active AND no execution result)` |
| **Test Run Duration** | Продолжительность тестового прогона текущего CI-запуска | `testRunDurationMs`, формат `Xm Ys` |

В знаменатель **Pass Rate** не входят `DISABLED`, `SKIPPED` и `NOT_RUN`. Если выполненных тестов нет, значение должно трактоваться как неопределённое; проверяйте поле `passRate` в источнике.

**Пример:**

```text
Passed = 73
Failed = 7
Broken = 0

Pass Rate = 73 / (73 + 7 + 0) × 100% = 91,25%
```

**Test Run Duration** берётся из записи `history.json`, соответствующей **ID и попытке именно оцениваемого CI-запуска**, а не из произвольной самой свежей записи. Это длительность прогона, не среднее по истории.

**Источник:** `target/metrics/test-run.json` (`summary`, `tests`) и `target/metrics/history.json` (длительность).

## 5. Historical Test Results

Исторические показатели считаются по сохранённым CI-запускам, а не только по последнему прогону.

### 5.1. Average Pass Rate

**Что показывает:** среднее арифметическое Pass Rate по доступным запускам из окна до 10 последних CI-запусков ветки.

```text
Average Pass Rate = (Pass Rate 1 + Pass Rate 2 + ... + Pass Rate N) / N
```

Где `N` — количество подходящих записей с корректным `passRate` и веткой. Старые записи без `passRate` не участвуют. Каждый CI-запуск имеет **одинаковый вес**, независимо от количества тестов.

**Пример:** 90%, 80%, 100% → `(90 + 80 + 100) / 3 = 90%`.

**Не путать** со сводным отношением суммы Passed ко всем выполненным тестам во всех запусках: это другая метрика.

**Источник:** `history.json`, поле `passRate`.

### 5.2. Flaky Rate

**Что показывает:** долю тестов, которые в историческом окне демонстрировали **как успешные, так и неуспешные результаты** без обязательного подтверждения изменения кода.

**Кандидат во flaky:** тест с минимум **3 наблюдениями** за последние **до 10 CI-запусков одной ветки**, среди которых присутствуют и успешные, и неуспешные результаты.

```text
Flaky Rate (%) = Flaky Candidates / Analyzed Tests * 100
```

`Analyzed Tests` — знаменатель, сформированный историческим сборщиком; не следует автоматически приравнивать его к `Total Tests`.

**Пример:** 6 кандидатов / 80 анализируемых тестов × 100% = **7,5%**.

**Ограничение:** перемежающиеся результаты могут объясняться изменениями приложения, тестовых данных или окружения. Поэтому это **кандидаты на нестабильность**, а не доказанный flaky-дефект. При недостаточной истории — `N/A`.

**Источники:** `test-history.json`, `flaky-metrics.json`; поле `candidateTestIds` помогает найти кандидатов.

### 5.3. Average Test Run Duration

**Что показывает:** среднюю длительность прогона за последние до 10 CI-запусков ветки с корректной длительностью.

```text
Average Duration (ms) = (Duration 1 + Duration 2 + ... + Duration N) / N
```

Записи без длительности не участвуют. Значение отображается как `Xm Ys`.

**Пример:** 180, 210 и 150 секунд → `(180 + 210 + 150) / 3 = 180 с = 3m 0s`.

**Источник:** `history.json`, поле `testRunDurationMs`.

## 6. Critical Tests & Feature Coverage

Критические тесты определяются уровнем `@Severity(SeverityLevel.CRITICAL)`.

| Метрика | Что означает | Формула / правило |
|---|---|---|
| **Critical Tests** | Все тесты с `CRITICAL` | `COUNT(severity = CRITICAL)` |
| **Critical Tests Passed** | Успешные критические тесты | `COUNT(CRITICAL AND PASSED)` |
| **Critical Tests Pass Rate** | Успешность выполненных критических тестов | `Critical Passed / (Critical Passed + Critical Failed/Broken) × 100%` |
| **Critical Tests Failed / Broken** | Неуспешные критические тесты | `COUNT(CRITICAL AND status IN (FAILED, BROKEN))` |
| **Critical Tests Disabled** | Отключённые критические тесты | `COUNT(CRITICAL AND disabled = true)` |
| **Critical Feature Coverage** | Доля критических функций, имеющих связь с тестом | `Covered Critical Features / Total Critical Features × 100%` |

**Пример Critical Tests Pass Rate:** 47 успешных и 7 неуспешных критических тестов:

```text
47 / (47 + 7) × 100% ≈ 87,0%
```

**Пример Critical Feature Coverage:** 16 покрытых критических функций из 16 → **100%**.

**Важно:** Critical Feature Coverage измеряет **наличие связи критической функции с автотестом**, а не факт успешного выполнения. Поэтому 100% покрытия может сочетаться со статусом `NOT_READY`.

Связь функций с тестами задаётся согласованным списком критических функций и идентификаторами задач/тестов (например, через `@Issue`/`issues` в инвентаризации). Фактические правила сопоставления определяются `ReleaseReadinessCollector`.

**Источники:** `release-readiness.json` (`criticalTests`, `criticalFeatureCoverage`), `test-inventory.json`.

## 7. API Coverage

Покрытие вычисляется по отчёту **Swagger Coverage**.

| Метрика | Что означает | Формула / правило |
|---|---|---|
| **Covered Checks** | Количество покрытых условий | `covered` |
| **Total Checks** | Всего учитываемых условий | `all` |
| **API Coverage** | Процент покрытых условий | `covered / all × 100%` |
| **Minimum Target** | Целевой минимум покрытия | `minCoveragePercent` |

**Пример:**

```text
Covered Checks = 51
Total Checks   = 2969

API Coverage = 51 / 2969 × 100% ≈ 1,72%
Minimum Target = 50%
```

**Принципиально:** это **не процент покрытых endpoint-ов** и не доля покрытых методов Java. Swagger Coverage учитывает условия/проверки из API-спецификации. Один endpoint может давать несколько условий.

На текущем Dashboard **Minimum Target — информационный ориентир**; сам по себе этот показатель не блокирует CI.

**Источник:** `target/metrics/api-coverage.json`.

## 8. Team Efficiency

Этот раздел состоит из двух независимых частей: восстановление отключённых тестов и время согласования Pull Request.

### 8.1. Соглашение для регистрации дефекта теста

Используется стандартная JUnit-аннотация `@Disabled` с префиксом **`BUG:`**:

```java
@Test
@Disabled("BUG: Button locator changed")
@Severity(SeverityLevel.CRITICAL)
void shouldCreatePatient() {
    // ...
}
```

Только `disabled = true` **и** `disabledReason`, начинающийся с `BUG:`, открывают цикл починки. Обычный `@Disabled("Feature not implemented")` в расчёте не участвует.

**Начало цикла:** первый учтённый CI-запуск, в котором тест обнаружен с `@Disabled("BUG: ...")`.

**Окончание:** следующий учтённый CI-запуск, в котором **тот же test ID**:
1. больше не отключён (`disabled = false`);
2. присутствует в `test-run.json` со статусом `PASSED`.

Простое удаление аннотации без успешного прогона **не закрывает** цикл. При повторном появлении `BUG:` после восстановления начинается новый цикл.

> **Что измеряем:** время от обнаружения маркера в CI до подтверждённого восстановления, а не чистое время работы инженера. Если `BUG:` обозначает ошибку самого OpenMRS, показатель включает ожидание исправления продукта.

### 8.2. Average Test Repair Time

**Что показывает:** среднюю длительность завершённых циклов восстановления за последние 30 календарных дней.

Для каждого закрытого цикла:

```text
Repair Time (test i) = repairedAt (test i) - detectedAt (test i)
```

Общая формула:

```text
Average Test Repair Time = (Repair Time 1 + ... + Repair Time N) / N
```

В расчёт входят циклы со временем `repairedAt` внутри последних 30 дней. Незавершённые циклы в среднее не включаются.

**Пример:** три теста восстанавливались 6, 12 и 30 часов:

```text
Average Test Repair Time = (6 + 12 + 30) / 3 = 16h 0m
```

При отсутствии завершённых циклов — `N/A`.

### 8.3. Tests Under Repair

**Что показывает:** количество **открытых циклов** с `BUG:` в текущей отслеживаемой ветке.

```text
Tests Under Repair = COUNT(cycles where status = OPEN)
```

**Пример:** два теста помечены `BUG:` и пока не подтвердили восстановление → **2**.

### 8.4. Repaired Tests

**Что показывает:** количество **закрытых циклов починки** за последние 30 дней.

```text
Repaired Tests = COUNT(cycles where status = REPAIRED
                       AND repairedAt >= now - 30 days)
```

Повторная поломка одного теста после восстановления создаёт новый цикл; следовательно, в течение месяца один и тот же test ID может дать больше одного закрытого цикла.

### 8.5. Average PR Approval Time

**Что показывает:** среднее время от готовности PR к ревью до **первого** подтверждённого `APPROVED` review от человека.

Для каждого PR:

- **Начало:** `created_at` обычного PR либо последнее событие `ready_for_review` до первого approval.
- **Конец:** время первого `APPROVED` review, оставленного не автором PR и не ботом.
- **Период:** PR, впервые получившие approval в последние 30 календарных дней.
- Draft PR без надёжного события готовности исключается; PR без approval тоже исключается.

```text
PR Approval Time (PR i) = firstApprovalAt (PR i) - reviewReadyAt (PR i)
```

```text
Average PR Approval Time = (PR Approval Time 1 + ... + PR Approval Time N) / N
```

**Пример:** три PR получили первый approval через 2, 5 и 8 часов:

```text
Average PR Approval Time = (2 + 5 + 8) / 3 = 5h 0m
```

Это **время до первого approval**, а не время до merge, не время до первого комментария и не суммарное время всех ревью.

**Источник:** GitHub REST API; `infra/collect_pr_approval_metrics.sh`.

### 8.6. PRs Awaiting Approval

**Что показывает:** текущее количество открытых PR, готовых к ревью и ожидающих одобрения. Draft PR не учитываются. Для репозиториев с правилами ревью GitHub возвращает `reviewDecision = REVIEW_REQUIRED`; если правила отсутствуют и `reviewDecision = null`, учитываются PR без актуальных `APPROVED` и `CHANGES_REQUESTED` в `latestReviews`.

```text
PRs Awaiting Approval = COUNT(
    state = OPEN
    AND draft = false
    AND (reviewDecision = REVIEW_REQUIRED
         OR (reviewDecision = null AND no latest APPROVED/CHANGES_REQUESTED reviews))
)
```

**Важное ограничение:** PR с `CHANGES_REQUESTED` при отсутствии правил защиты ветки не включается в очередь ревьюеров, поскольку обычно ожидает доработки автора. Для точной интерпретации решения по ревью рекомендуется включить branch protection / rulesets.

### 8.7. PRs Ready To Merge

**Что показывает:** текущее количество открытых PR, имеющих действующее одобрение и готовых к merge по данным GitHub.

```text
PRs Ready To Merge = COUNT(
    state = OPEN
    AND draft = false
    AND reviewDecision = APPROVED
    AND mergeStateStatus = CLEAN
)
```

`mergeStateStatus = CLEAN` означает, что GitHub считает PR готовым к слиянию, включая отсутствие конфликтов и блокирующих обязательных проверок. Значения `BLOCKED`, `DIRTY`, `UNSTABLE`, `BEHIND`, `DRAFT` и `UNKNOWN` не засчитываются. Если репозиторий не настроен требовать review, `reviewDecision` может быть `null`, и такие PR не попадут в **Ready To Merge** до настройки правил одобрения.

Обе метрики — **моментальный снимок текущей очереди**, а не статистика за 30 дней. Они рассчитываются через GitHub GraphQL API, в отличие от **Average PR Approval Time**, использующей REST API и 30-дневное окно.

### 8.8. Пример полного цикла

| Событие | Время |
|---|---|
| CI впервые увидел `@Disabled("BUG: ...")` | Пн 10:15 |
| Исправление отправлено в PR | Вт 12:00 |
| Первый approval PR | Вт 13:00 |
| CI увидел активный тест и `PASSED` | Вт 14:30 |

Результат:

- **Test Repair Time:** 28 ч 15 мин (Пн 10:15 → Вт 14:30).
- **PR Approval Time:** определяется **от времени готовности PR к ревью**, а не от начала починки; если PR был готов во Вт 12:00, то **1 ч**.
- **Repaired Tests:** +1 закрытый цикл.
- **PRs Awaiting Approval / Ready To Merge:** отражают текущий статус PR; после merge он не входит ни в одну из двух метрик.

Эти показатели намеренно независимы: PR может не быть связан с отключённым тестом, а восстановление теста может происходить через несколько PR.

## 9. Источники данных и обновление

| Файл | Содержимое | Где используется |
|---|---|---|
| `test-inventory.json` | Все тесты, тип, severity, disabled/reason, issues | Overview, критичность, начало/окончание ремонта |
| `test-run.json` | Результаты текущего запуска и summary | Last Results, подтверждение ремонта |
| `release-readiness.json` | Статус, причины, критические тесты/функции | Release Readiness, Critical |
| `history.json` | История CI, Pass Rate, длительности | Historical Results, Test Run Duration |
| `test-history.json` | История результатов отдельных тестов | Flaky Rate |
| `flaky-metrics.json` | Рассчитанные flaky-кандидаты и доля | Flaky Rate |
| `api-coverage.json` | Covered/Total Checks и цель | API Coverage |
| `test-repair-history.json` | Открытые и закрытые циклы `BUG:` | Исторический источник для ремонта |
| `test-repair-metrics.json` | Среднее время, открытые/закрытые циклы | Team Efficiency |
| `pr-approval-metrics.json` | Среднее время approval и текущие очереди PR | Team Efficiency |

**Процесс обновления:**

1. GitHub Actions получает артефакты тестового прогона.
2. Сборщики формируют JSON-метрики.
3. Исторические данные восстанавливаются из предыдущей публикации и дополняются новым запуском.
4. `MetricsDashboardGenerator.java` объединяет JSON и создаёт HTML.
5. Workflow публикует Dashboard и историю в `gh-pages`.

**Bash-скрипты новых метрик:**

```bash
bash infra/update_test_repair_history.sh \
  --history target/metrics/test-repair-history.json \
  --inventory target/metrics/test-inventory.json \
  --test-run target/metrics/test-run.json \
  --output target/metrics/test-repair-metrics.json \
  --branch "$TEST_BRANCH" \
  --run-id "$TEST_RUN_ID" \
  --attempt "$TEST_RUN_ATTEMPT" \
  --completed-at "$TEST_COMPLETED_AT"

bash infra/collect_pr_approval_metrics.sh \
  --output target/metrics/pr-approval-metrics.json
```

Для второго скрипта необходимы `GITHUB_TOKEN`, `GITHUB_REPOSITORY`, доступ к GitHub REST API и `jq`/`curl`. Первый использует Bash, `jq` и GNU `date`.

## 10. Ограничения и правила интерпретации

1. **Не смешивать покрытие и качество:** Critical Feature Coverage 100% не означает 100% успешных тестов; API Coverage не равно проценту endpoint-ов.
2. **Не смешивать уровни агрегации:** Total Tests — число уникальных тестов; количество JUnit-инвокаций может быть выше.
3. **История ограничена:** Average Pass Rate и Average Duration используют до 10 запусков, а Team Efficiency — 30 дней. Поэтому показатели нельзя напрямую сравнивать как одно временное окно.
4. **Flaky Rate — индикатор:** историческое чередование статусов не доказывает, что причина именно в тесте.
5. **`@Disabled("BUG: ...")` — дисциплина команды:** если метку забыли поставить, цикл не будет зарегистрирован. Если метку поставили из-за продуктового бага, длительность включает ожидание продукта.
6. **Удаление/переименование теста:** само исчезновение test ID не подтверждает починку. При переименовании ID история может перестать связываться автоматически.
7. **PR Approval Time — не lead time:** время от создания/готовности PR до первого approval не равно времени доставки изменения в основную ветку.
8. **`N/A` — не 0:** отсутствие наблюдений нельзя считать хорошим или плохим результатом.
9. **Ветки и повторы:** история привязывается к ветке и CI run/attempt; смешивание веток и повторная обработка одного запуска способны исказить тренды. Сборщик ремонта защищён от повторной обработки одного run/attempt.
10. **Дашборд отображает расчёты:** при изменении бизнес-правил нужно синхронно обновлять сборщик, JSON-схему, HTML и этот документ.
